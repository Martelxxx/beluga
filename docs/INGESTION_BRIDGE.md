# Beluga ingestion → passenger bridge (feature branch)

## Purpose

Connect the published airport-specific knowledge generated by the ingestion backend
to the existing Beluga passenger composer, header image and Dynamic Hub without
removing the Duffel, RouteStack, flight-status, feedback, or existing agent paths.

This branch targets the GitHub **V52.1** backend. The separate Beluga 2.0 v46
ZIP is not part of this repository; its exact header and Dynamic Hub component
binding must be completed against those source files before claiming a fully
integrated Beluga 2.0 release.

## Publication boundary

The ingestion service remains the authoritative collector and verifier. The
passenger API consumes only a **published**, QA-passed snapshot. An interrupted
crawl, draft or unverified dossier must never replace a published passenger
version. The ingestion operator must enforce the **current passing audit and
matching context fingerprint** before constructing `qa.passed: true`.

Set a strong, random shared secret in the passenger server's `.env`:

```text
BELUGA_INGESTION_PUBLISH_KEY=<long-random-secret>
BELUGA_INGESTION_RETRIEVE_URL=
BELUGA_INGESTION_SERVICE_TOKEN=
```

`BELUGA_INGESTION_RETRIEVE_URL` is the optional **server-side** published
semantic evidence retrieval endpoint exposed by the ingestion service.
It must accept POST JSON:

```json
{"airport":"IAD","question":"coffee near C12","published_revision":"iad-v10-0001","limit":6}
```

and return **original source** passage excerpts, not LLM-created dossiers:

```json
{"evidence":[{"text":"Coffee shop at C12...", "source_url":"https://airport.example/dining",
"title":"Dining guide"}]}
```

When this endpoint is absent/unavailable, Beluga falls back to a bounded
lexical search of the snapshot's original-source excerpts; the API labels this
`published-fallback`, never `semantic`. Live waits, gates and open/closed
status still require their respective real-time feeds.

## Passenger snapshot contract

After successfully completing its publish QA, the ingestion operator sends
`POST /api/ingestion/publish` with `X-Beluga-Publish-Key`. Example:

```json
{
  "airport": "IAD",
  "airport_name": "Washington Dulles International Airport",
  "revision": "iad-v10-20261017-01",
  "published_at": "2026-10-17T22:00:00Z",
  "qa": {
    "passed": true,
    "context_fingerprint": "REPLACE_WITH_ACTUAL_PASSED_CONTEXT_FINGERPRINT"
  },
  "header_image": {"url": "https://example.org/published/dulles-header.jpg"},
  "concessions": [
    {"name": "Cafe", "terminal": "C", "gate": "C12",
     "website": "https://example.org/cafe", "source_url": "https://example.org/dining"}
  ],
  "coupons": [],
  "checkpoints": [
    {"name": "East security", "location": "Departures", "source_url": "https://example.org/security"}
  ],
  "maps": [],
  "gate_routes": [],
  "facts": [
    {"text": "The AeroTrain connects the main terminal and midfield concourses.",
     "source_url": "https://example.org/transport"}
  ],
  "evidence": [
    {"text": "Source passage copied from the airport's current published page...",
     "source_url": "https://example.org/transport"}
  ]
}
```

For an image file instead of URL, supply:

```json
"header_image": {"mime_type": "image/png", "data_base64": "BASE64_OF_PNG"}
```

Accepted types: PNG, JPEG or WebP, maximum 2.5 MB; only HTTPS external images.
Use `tools/publish_airport.py` to attach an image and send a manifest to the
passenger backend without manually generating base64.

## Read API

- `GET /api/ingestion/airports` — list published airport codes
- `GET /api/ingestion/airport/IAD` — published header, concessions, maps, checkpoints, metadata and revision
- `GET /api/ingestion/image/IAD` — published header image (when binary was uploaded)
- `POST /api/ingestion/retrieve` — retrieve source-grounded passages for the Dynamic Hub, request `{"airport":"IAD","question":"coffee near C12"}`
- `POST /api/chat` — unchanged caller contract; now uses current published context/evidence before the previously bundled IAD JSON when relevant

### Passenger UI contract

`assets/ingestion-client.js` is injected into the existing passenger HTML by
`beluga_server.py`. It exposes:

```js
await window.BelugaIngestion.setAirport("IAD");
const profile = await window.BelugaIngestion.getProfile("IAD");
const {evidence, mode} = await window.BelugaIngestion.retrieve("coffee near gate C12");
document.dispatchEvent(new CustomEvent("beluga:airport-changed", {detail:{airport:"EWR"}}));
```

For automatic header updates, give the actual header image (or background
container) `data-beluga-airport-header`, or use its recognized
`#airportHeroImage` / `#airportHeaderImage` ID. The app should emit
`beluga:airport-changed` as part of changing its own airport state.
The bridge fires `beluga:ingestion:updated` with
`{airport, profile, available}` for the Dynamic Hub to render verified
concession cards, websites, maps and checkpoint information.

The bridge deliberately does **not** invent Dynamic Hub cards or replace its
existing dispatch/router. That is a view-specific binding in the newer
Beluga 2.0 release.

## Demo readiness: October 21/23

- #6 terminal concessions: ready when a real, published concessions snapshot is provided and the Dynamic Hub binds profile data.
- #7 coupons: display plumbing only; actual redeemable offers need merchant supply and validation.
- #9 passenger metrics: not implemented by this bridge; analytics/instrumentation is separate.
- #10 gate walk times: route facts/maps can be ingested; accurate distance, graph navigation and real-time position are separate.
- #11 TSA waits: checkpoint metadata can be ingested; live waits need a current source.
- #12 geofencing: no device location boundary logic is added by this bridge.
- #14 airport autosensing: airport switching supported; device location sensing still needs its own permission and lookup logic.
- Q-SYS PA, translation, sign language, voice cloning, priority audio and mobility support remain separate workflows.
